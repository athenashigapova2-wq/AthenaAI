# Baseline: 5 users x 5 iterations

Date: 2026-08-21
Scenario: `baseline-5x5`
Target: local Docker Compose stack with the real GigaChat provider

## Load profile

- Virtual users: 5
- Ramp-up: 30 seconds
- Iterations per user: 5
- Planned E2E scenarios: 25
- Celery worker concurrency: 4 threads

The test gradually started approximately one virtual user every six seconds.
Each E2E scenario enqueued one agent job and polled it until a terminal status.
The profile has no fixed duration: it ends after every virtual user completes
all five iterations.

## Measured path

1. `POST /api/v1/agent/chat` enqueues the job and must return HTTP 202.
2. `GET /api/v1/agent/chat/jobs/{job_id}` polls until `succeeded` or `failed`.

The authenticated token preflight runs before JMeter and is excluded from the
measured samples. The Vite frontend is also outside the measured path.

## Environment

- Windows 11 host with Docker Desktop and WSL2 Linux containers
- FastAPI API exposed locally on port 8001
- Redis 7.4 Alpine broker and job store
- Celery 5.4 worker using a four-thread pool
- Remote Supabase database and authentication
- Real GigaChat provider calls
- Apache JMeter 5.6.3 in non-GUI mode
- JMeter Backend Listener to InfluxDB 2.7
- Grafana 12.4 provisioned dashboard

Latency percentiles were calculated from all 25 parent `agent_chat_e2e` rows in
the JTL file using the nearest-rank method. E2E throughput is the number of
completed parent scenarios divided by the complete test span. HTTP throughput
counts only POST enqueue and GET polling requests; it excludes the parent
transaction and JMeter assertions.

Grafana receives five-second aggregates from the JMeter Backend Listener, so its
charts show interval percentiles. The JTL values above are the authoritative
full-run summary.

## Conclusion

The system completed the entire 5 x 5 profile without failed or missing jobs.
This run is the current real-provider baseline for later comparisons. The peak
number of simultaneously active users may be lower than five because the
30-second ramp-up starts users gradually and early users can finish before the
last user starts.
